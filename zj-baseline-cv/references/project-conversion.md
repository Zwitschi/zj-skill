# Project conversion

Detailed instructions for the project-conversion part of the `zj-baseline-cv`
skill. Use it only when the candidate's CV is task-based and the candidate wants
project-based material for contracting or freelance applications.

## Preconditions

1. The current CV is available.
2. The CV is task-based: bullets describe responsibilities and duties rather
   than discrete projects.
3. If the CV is already project-based, say so and stop. Do not convert it again.
4. The candidate has chosen the output language.

## Role loop

- Process one role at a time, in chronological order.
- State the total number of roles before starting.
- State the total number of projects and the total number of questions for the
  role before the project interview.
- Do not move to the next role until the candidate confirms the current role is
  complete. Silence is not confirmation.
- Allowed confirmation: "next role", "done", or an equivalent explicit phrase.

## Project interview

For each role, ask: "Within this role, which individual projects did you carry
out?"

For each project, ask the following fields one at a time, waiting for an answer
or an explicit skip:

| Field                                   | Question focus                                                          |
| --------------------------------------- | ----------------------------------------------------------------------- |
| Period                                  | Start and end, or duration                                              |
| Industry                                | Sector and client context                                               |
| Project team                            | Team size and the candidate's place in it                               |
| Assignment role                         | The role the candidate performed on the project                         |
| Environment                             | Technologies, systems, methods                                          |
| Initial situation                       | The problem or starting state                                           |
| Project                                 | What was done                                                           |
| Challenges                              | Special aspects, constraints, hard parts                                |
| Result or impact                        | What changed, tagged exact, estimated, or approximate                   |
| Client and assignment context, optional | End client, intermediary, contract type, work mode, assignment language |

The candidate may skip the optional context field entirely.

## Evidence rules for the interview

- Never invent project details, dates, team sizes, technologies, outcomes, or
  client names.
- If a detail is unknown, leave the field blank and mark it `[TO CONFIRM]`
  rather than estimating.
- If there is no measurable outcome, ask for a qualitative result instead of
  leaving the field empty.
- Tag every result or impact figure as exact, estimated, or approximate.
- Never merge or summarise projects at this stage. Each project gets its own
  entry, even within one role.

## Output A: CV short version

- Three to five bullets per role.
- Format: activity, then the result.
- Impact-led rather than task-led.
- Concise enough for the main CV.
- Do not exceed normal CV length; this is a summary, not the full project
  detail.
- Mark a bullet that already carries a tagged, quantified outcome with
  `[QUANTIFIED]`.

## Output B: Project list entry

Use the exact field structure from the interview. The output must drop directly
into a project-list appendix without reformatting.

If the candidate has an existing project-list template, match its field order
and labels. Do not invent fields the template does not contain.

## Availability and closing note

After all roles are processed, ask once:

- current availability, such as a date or "immediately";
- preferred engagement mode: remote, onsite, hybrid;
- travel radius, if relevant;
- whether a "references on request" line should be added.

Add the availability line only if provided. Omit it if declined. Do not invent a
notice period, permit status, or travel willingness.

## Final assembly

Once all roles are confirmed:

1. Assemble all CV short versions into one continuous, chronological work
   experience section.
2. Assemble all project entries into one standalone project list.
3. Preserve the `[QUANTIFIED]` markers for handoff.
4. Mark every unconfirmed field with `[TO CONFIRM]`.
5. Label the result as a working draft for candidate review, not a final
   submission.

## Handoff

The short-version output feeds the evaluation and tailoring skills. Preserve:

- `[QUANTIFIED]` markers;
- source tags;
- `[TO CONFIRM]` items;
- the project field structure.

The evaluation skill must not ask again for an outcome already captured and
tagged here.

## Quality checklist

- The input CV was task-based and the stop condition did not apply.
- Every role was processed in order and explicitly confirmed.
- Every project has its own entry.
- Unconfirmed fields are marked, not guessed.
- Figures are tagged exact, estimated, or approximate.
- The CV short version is three to five bullets per role.
- The project list uses the agreed field structure.
- Availability and references lines are included only if confirmed.
- The output is labelled as a working draft.
